# Протокол ХатаВойс: журнал, подписанные запросы, события

Этот документ описывает, что ходит между клиентом и сервером ХатаВойс: журнал, подписанные запросы и события (блок А1 «Личность, роли и модерация»), защищённое соединение и сквозное шифрование звонков (блок А2а «Защищённое соединение и шифрование звонков»). Здесь — точные форматы, по которым можно написать совместимый клиент или проверить чужой. Примеры закреплены тестами: в разделе 8 — `crates/hv-roster/tests/protocol_vectors.rs`, в разделе 10.8 — `crates/hv-crypto/tests/protocol_vectors.rs`. Если формат поменяется, тест упадёт.

Содержание: 1–8 — ключи, журнал, запросы, события; 9 — TLS и ключ сервера; 10 — звонки (пересыльщик, `CallCredential v1`, ключи кадров, код звонка); 11 — чего протокол не защищает.

## 1. Ключи и имена

- Личность — ключ Ed25519. Публичный ключ, подпись и хеши в JSON записываются как **base64url без `=`**.
- `user_id` — первые 16 байт SHA-256 публичного ключа в base32 (RFC 4648, без `=`), строчными буквами. Пример: `gr2q7gf5lh6pzfdnurnkvputhm`.
- Отпечаток для людей — первые 4 символа `user_id` (`gr2q`). Его показывают рядом с ником, если ники совпадают.
- У сервера свой ключ SK. Клиент запоминает его при первом знакомстве и сверяет при каждом подключении.

## 2. Журнал участников

Журнал — цепочка записей. Каждая запись подписана автором, сервер только хранит и раздаёт их; любой участник проверяет весь журнал сам.

```json
{
  "seq": 0,
  "prev": "<SHA-256 предыдущей записи; у первой — 32 нулевых байта>",
  "at": 1800000000,
  "author": "<публичный ключ автора>",
  "body": { "type": "genesis", "...": "..." },
  "signature": "<подпись автора>",
  "invite_signature": "<только у join: подпись ключом приглашения>",
  "server_signature": "<только у genesis: подпись ключом SK>"
}
```

**Что подписывается.** Байты JSON-объекта ровно в таком порядке полей, без пробелов:

```
{"domain":"hatavoice-roster-v1","seq":…,"prev":"…","at":…,"author":"…","body":{…}}
```

Все подписи записи (`signature`, `invite_signature`, `server_signature`) — над этими же байтами.

**Хеш записи** (следующая запись кладёт его в `prev`): SHA-256 от подписанных байтов, к которым дописаны 64 байта `signature`, затем, если есть, `invite_signature` и `server_signature`.

**Виды записей** (`body.type`):

| `type` | Поля | Кто может |
|---|---|---|
| `genesis` | `server_name`, `owner`, `server_key` | только первая запись; подписана и владельцем, и SK |
| `role_create`, `role_update` | `id`, `name`, `color`, `permissions` | `manage_roles`, роль ниже своей |
| `role_delete` | `id` | `manage_roles` |
| `role_order` | `ids` — все роли снизу вверх, `everyone` первая | `manage_roles` |
| `member_roles` | `user`, `roles` | `manage_roles`, человек и роли ниже тебя |
| `invite_create` | `invite` (публичный ключ), `roles`, `max_uses`, `expires_at` | `create_invites` |
| `invite_revoke` | `invite` | `create_invites` |
| `join` | `user`, `invite` | сам новичок + подпись ключом приглашения |
| `leave` | — | любой, кроме владельца |
| `kick` | `user`, `reason`, `media` | `kick_members`, по иерархии |
| `ban` | `user`, `until` (или `null` — навсегда), `reason`, `media` | `ban_members`, по иерархии |
| `unban` | `user` | `ban_members` |
| `owner_transfer` | `to` (`user_id`) | владелец; бывший владелец получает роль `admin` |
| `server_profile` | `name`, `description`, `welcome`, `icon` | `manage_server` |
| `server_settings` | `afk_channel`, `afk_minutes` ∈ {0, 5, 15, 30, 60}, `history_days` ∈ {0, 7, 30, 90} (сколько дней чата получает новичок; нет поля — 30) | `manage_server` |
| `channel_create`, `channel_update` | `id`, `name`, `user_limit` (0–99), `overrides`, `kind` (`"voice"` по умолчанию или `"text"`; `voice` не пишется, поэтому старые записи сериализуются байт в байт как раньше) | `manage_channels` |
| `channel_delete` | `id` | `manage_channels` |
| `channel_order` | `ids` | `manage_channels` |

Права: `manage_server`, `manage_roles`, `manage_channels`, `create_invites`, `view_audit_log`, `mute_members`, `move_members`, `kick_members`, `ban_members`, `connect`, `speak`, `stream`. Права канала по ролям: `{role, view, connect, speak}`, каждое — `inherit` / `allow` / `deny`. Правила иерархии и итоговые права канала — разделы 4.3 и 4.4 спецификации.

`MediaRef` — `{sha256, mime, size}`: ссылка на файл, загруженный на этот сервер.

## 3. `hello`: сервер доказывает свой ключ

`GET /api/hello?nonce=<1–64 символа от клиента>` — без подписи. Ответ:

```json
{ "server_key": "…", "owner": "…", "name": "Хата", "roster_len": 12, "roster_head": "…", "proof": "…" }
```

`proof` — подпись SK над `hatavoice-hello-v1\n{nonce}\n{roster_head}`. Клиент проверяет подпись и сверяет `server_key` с запомненным (или с ключом из приглашения). Несовпадение — «Сервер по этому адресу подменён или переустановлен», подключение останавливается.

## 4. Подписанные запросы

Все запросы участника (кроме `hello`, `GET /api/invite` и `GET /api/media/{sha}`) несут заголовок

```
Authorization: HV1 <base64url(JSON {"u": публичный ключ, "t": время, "n": nonce, "s": подпись})>
```

Подписываются байты:

```
hatavoice-req-v1
{SK}
{МЕТОД}
{путь?запрос}
{t}
{n}
{SHA-256 тела в hex, строчными}
```

Сервер принимает запрос, если подпись верна, `t` отличается от его часов не больше чем на 60 секунд и такой `n` не приходил последние 120 секунд. Ответы с ошибкой: `401 {"error", "clock_skew": true, "server_time"}` — часы клиента расходятся с сервером; `401` «Этот запрос уже был отправлен» — повтор; `403 {"join_needed": true}` — не участник; `403 {"banned": true, "until"}`; `503 {"unclaimed": true}` — у сервера ещё нет владельца.

## 5. Приглашения

Ссылка: `hatavoice://<адрес>:<порт>/#v=1&sk=<SK>&inv=<семя ключа приглашения>[&by=<ник>]`; `by` — ник того, кто сделал ссылку, base64url UTF-8, 1–32 символа (негодный не мешает разобрать ссылку). Всё после `#` не уходит на сервер. Клиент:

1. делает `hello` и сверяет SK со ссылкой;
2. `GET /api/invite?key=<публичный ключ приглашения>` — без подписи: `{server_name, description, welcome, icon, inviter, roles, valid}`; ник пригласившего сервер не знает — он во фрагменте ссылки (`by`);
3. подписывает запись `join` своим ключом и ключом приглашения и шлёт `POST /api/roster`.

Сервер не знает семени приглашения и не может впустить кого-то сам. Секрет хранится только в ссылке: создатель видит её один раз.

## 6. Остальной API

| Метод и путь | Что делает |
|---|---|
| `GET /api/roster?from=N` | записи журнала с номера N: `{entries: [...]}` |
| `POST /api/roster` | дописать запись; `409 {"conflict": true}` — кто-то успел раньше, перечитать и подписать заново |
| `GET /api/state` | живое состояние: `{online, occupancy, mutes, server_time}`; `online` — id тех, у кого открыт поток событий; занятость — только видимых тебе каналов |
| `PUT /api/profile`, `PUT /api/presence` | `410 {"error": "Обнови ХатаВойс"}`: ники, цвета и «Играет в …» сервер не хранит — они идут через группу сервера (§11.4); `profiles.json` прежней версии удаляется при старте |
| `POST /api/voice/token` | `{channel}` → `{url, token}` — пропуск LiveKit на 5 минут; сервер сам ставит личность (id участника) и право говорить; имени в пропуске нет — ник окно берёт из группы. Программа отдаёт окну вместо `url` адрес своего локального моста (9.5) |
| `POST /api/call/{channel}/create`, `…/join`, `…/commit`, `GET /api/call/{channel}?since=N` | пересыльщик групп звонков — раздел 10.3 |
| `POST /api/moderation` | команда: `{action: "mute", user, minutes ∈ {5,15,60,1440} или null, reason}`, `{action: "unmute", user}`, `{action: "move", user, channel}`, `{action: "disconnect", user}` |
| `GET /api/audit?user&kind&before` | журнал действий (право `view_audit_log`), новые сначала |
| `POST /api/media?purpose=moderation\|icon` | загрузить файл (тело — сами байты): GIF/MP4/WebM до 8 МБ или PNG/JPEG/GIF/WebP до 1 МБ; тип по сигнатуре → `MediaRef` |
| `GET /api/media/{sha256}` | файл по хешу, без подписи — чтобы гифку увидел и уже кикнутый |

## 7. Поток событий

`GET /api/events` (WebSocket, подписанный). Сервер шлёт JSON-объекты с полем `type`:

- `roster {seq}` — новая запись журнала; `online {user, online}` — человек открыл первый поток событий или закрыл последний; `occupancy {channel, people}`;
- `mute {user, until, by, reason}`, `unmute {user}` — всем;
- `moved {channel, by}`, `disconnected {by}`, `kicked {by, reason, media}`, `banned {by, until, reason, media}` — только тому, кого касается;
- `moderation_notice {user, kind, reason, media}` — тем, кто был в голосовом канале с наказанным;
- `call_join`, `call_commit`, `call_welcome`, `call_reset` — только людям одного звонка, содержимое непрозрачно для сервера — раздел 10.4.

После `kicked`/`banned` сервер закрывает поток (код 4000) и больше не принимает запросы этого человека. После обрыва клиент переподключается с паузой 1 → 30 секунд и перечитывает журнал, чтобы не пропустить записи.

## 9. TLS и ключ сервера

Всё общение программы с сервером — запросы (разделы 3–6), поток событий (7), сигналинг LiveKit `/rtc` — идёт через один порт сервера (`api_port`, по умолчанию 7350) и только по TLS 1.3. Звук (и позже экран) идёт напрямую в порты LiveKit (UDP 7882, запасной TCP 7881) и в TLS не заворачивается: его защищают DTLS-SRTP и сквозной ключ звонка (раздел 10). Незашифрованного запасного режима нет ни в одну сторону.

### 9.1. Параметры TLS

| | Значение |
|---|---|
| Версия | только TLS 1.3; TLS 1.2 и старше не принимают ни сервер, ни клиент |
| Обмен ключами | только `X25519MLKEM768` (гибрид X25519 и ML-KEM-768, постквантовый). Сторона, которая предлагает другие группы, получает `handshake_failure` (alert 40) |
| Шифры | набор rustls (провайдер aws-lc-rs) по умолчанию для TLS 1.3; на практике `TLS_AES_256_GCM_SHA384` |
| Подпись рукопожатия | `ecdsa_secp256r1_sha256` (ключ листа) |
| Клиентские сертификаты | нет |
| Возобновление сессий | у клиента выключено: ключ сервера сверяется при каждом соединении |
| Имя сервера | клиент обращается к `https://<адрес>`, поэтому имя в рукопожатии — хост из адреса (для IP-адреса имя вообще не передаётся). Имя не проверяется; `hatavoice.invalid` лишь записано в SAN листа, настоящие клиенты его не используют |
| HTTP | только HTTP/1.1 (ALPN не объявляется), WebSocket — через `Upgrade` |
| Пределы соединения | до TLS — 10 секунд на первый байт и столько же на рукопожатие; заголовок запроса — за 30 секунд с того момента, как соединение ждёт запроса (поэтому соединение, простаивающее между запросами, закрывается через 30 секунд); посреди запроса — не больше 60 секунд без единого байта в любую сторону; один запрос, от заголовка до последнего байта ответа, — не дольше 5 минут. На соединения после `Upgrade` (поток событий, `/rtc`) эти пределы не действуют: у них свои пинги. Одновременно открыто не больше 256 соединений, считая WebSocket, и не больше 32 с одного адреса (IPv6 — с одной сети /64); следующее закрывается сразу. При выключении сервер ждёт запросы в работе не больше 5 секунд |

### 9.2. Сертификат сервера

Сервер отдаёт цепочку из двух сертификатов в порядке `[лист, издатель]`. Центра сертификации нет: издатель — сам ключ сервера SK (тот же, что подписывает `hello` и genesis журнала).

| | Издатель (второй) | Лист (первый) |
|---|---|---|
| Subject | `CN=HataVoice server` | `CN=hatavoice.invalid` |
| Issuer | `CN=HataVoice server` (самоподписанный) | `CN=HataVoice server` |
| Ключ | Ed25519 — это и есть SK | ECDSA P-256, **новый при каждом запуске сервера**, живёт только в памяти |
| Подписан | своим ключом (Ed25519) | ключом SK (Ed25519) |
| Расширения | Basic Constraints `CA:TRUE` (critical), Key Usage `keyCertSign` (critical) | SAN `DNS:hatavoice.invalid`, Extended Key Usage `serverAuth` |
| Срок | 1975-01-01 00:00:00 — 9999-12-31 00:00:00 UTC | тот же |

Срок так широк, чтобы время в проверке не участвовало: ПК с севшей батарейкой BIOS или без интернета подключается так же, как с верными часами. Подменить сертификат без SK нельзя, а ключ листа может утечь только из работающего сервера, у которого и так есть всё.

### 9.3. Правило проверки у клиента

1. В ответе не меньше двух сертификатов. Первый — лист, второй — издатель. Издатель не проверяется как сертификат (ни срок, ни подпись): значение имеет только его открытый ключ.
2. Ключ издателя должен быть Ed25519 (`SubjectPublicKeyInfo` = `302a300506032b6570032100` ‖ 32 байта). Эти 32 байта — «ключ, который показал сервер».
3. Если для адреса закреплён SK (из приглашения `sk=…` или сохранённый вместе с сервером) и показанный ключ другой, соединение рвётся с ошибкой «Сервер по этому адресу подменён или переустановлен — подключение остановлено».
4. Лист проверяется с единственным доверенным корнем — ключом издателя: подпись листа, назначение `serverAuth`. Время при проверке фиксировано (2000-01-01), часы ПК не читаются, имя не проверяется.
5. Подпись рукопожатия TLS 1.3 (`CertificateVerify`) проверяется обычным образом открытым ключом листа.

Закрепление ключа:

- Ключ задаёт приглашение (раздел 5) или сохранённый сервер. Дальше этим правилом проверяется каждое соединение: запросы, поток событий, мост окна.
- Если для адреса ключ ещё не закреплён (сервер открывают по адресу, без приглашения), клиент берёт ключ из рукопожатия и принимает его, только если одновременно `hello` по тому же соединению подтверждён подписью этого ключа и журнал сервера, проверенный целиком, начинается с genesis этого ключа и содержит самого клиента как участника. Записи `join` без ключа личности клиента не подделать, поэтому подставной сервер получает отказ «Ты не участник этого сервера».
- Исключения — только соединения с собственным сервером на `127.0.0.1`, которые не выходят за пределы ПК. Пока сервер не настроен (журнала ещё нет), ключ принимается из рукопожатия. Служебные запросы программы к своему серверу (`/api/host/status`, `/api/host/shutdown`, `/api/host/legacy-channels`) идут через клиент, который тоже берёт ключ из рукопожатия без сверки с журналом: в них нет секретов, а сервер отвечает на них только запросам с этого же ПК. После настройки ключ для обычных запросов закреплён.
- Для обычных запросов ключ в сертификате должен совпасть с `server_key` из `hello` и с ключом в genesis журнала.

### 9.4. Старые версии: ответ 426

Первый байт входящего соединения `0x16` — рукопожатие TLS. Любой другой (обычный HTTP от старой версии) получает ответ, после чего соединение закрывается:

```
HTTP/1.1 426 Upgrade Required
Upgrade: TLS/1.3
Connection: Upgrade, close
Content-Type: application/json
Content-Length: 108

{"error":"На сервере новая версия ХатаВойс — обнови программу"}
```

Старый клиент показывает поле `error` как есть. Сервер ждёт первый байт и рукопожатие не дольше 10 секунд, весь ответ отдаёт не дольше 5 секунд и читает из запроса не больше 64 КиБ.

Новый клиент на старом сервере получает в ответ на рукопожатие обычный текст, а не TLS, и пишет «Сервер на старой версии ХатаВойс — попроси хоста обновить». Сервер не отвечает или порт закрыт — «Сервер недоступен: …».

Ключ SK при обновлении не меняется, поэтому выданные приглашения и сохранённые серверы продолжают работать.

### 9.5. Окно программы: мост и `hvmedia`

Окно (WebView2) не может проверить сертификат, за который ручается только ключ сервера, поэтому само в сеть не ходит. Политика безопасности окна: `connect-src 'self' ipc: http://ipc.localhost ws://127.0.0.1:* http://127.0.0.1:*`, `img-src 'self' data: blob: http://hvmedia.localhost`, `media-src 'self' blob: http://hvmedia.localhost`; внешних `http:`, `https:`, `ws:`, `wss:` адресов в ней нет. Всё, что нужно окну, делает Rust-часть программы по TLS из 9.3.

**Мост сигналинга LiveKit.** Rust-часть при запуске открывает мост на `127.0.0.1:<случайный порт>`. Адрес, который окно получает вместо адреса LiveKit в ответе на `POST /api/voice/token`:

```
ws://127.0.0.1:<порт>/<секрет>/<адрес сервера>
```

- `<секрет>` — 32 случайных байта в base64url (43 символа), новые при каждом запуске программы: страница в браузере может перебирать порты на `127.0.0.1`, но секрета не знает;
- `<адрес сервера>` — адрес, под которым сервер открыт, в процентной кодировке (кроме латинских букв и цифр заменяется всё), например `127.0.0.1:7350` → `127%2E0%2E0%2E1%3A7350`;
- livekit-client сам дописывает `/rtc/v1?…` (запасной путь — `/rtc?…`) и `…/validate`.

Что пропускает мост: только путь `/rtc` или `/rtc/…` (после разбора `.` и `..`: `/rtc/../api/state` — 404) и только два вида запросов:

| Запрос окна | Что делает мост |
|---|---|
| WebSocket `…/rtc…` | открывает `wss://<адрес>/rtc…` по проверенному TLS и пересылает сообщения в обе стороны; закрылась одна сторона — закрывается и вторая |
| `GET …/validate` | отдаёт ответ сервера как есть (не больше 64 КиБ), добавляя `Access-Control-Allow-Origin: *`: livekit-client по нему отличает отказ в пропуске от обрыва сети |

Всё остальное — 404: неверный секрет, адрес, который программа не открывала, другой путь, другой метод. Если сервер показал не тот ключ, что закреплён, мост отвечает 502 с текстом про подмену.

**Картинки и гифки.** Адрес вида `http://hvmedia.localhost/<адрес сервера>%2F<sha256>`: путь — «адрес/хеш» одним куском в процентной кодировке (`sha256` — 64 символа hex строчными). Rust-часть скачивает `https://<адрес>/api/media/<sha256>` по проверенному TLS (не больше 16 МиБ), **сверяет SHA-256 полученных байтов с хешем из адреса** и только потом отдаёт окну. Не совпало — 502 «Файл на сервере подменён — он не совпал с хэшем». Тип файла — тот, что назвал сервер, если это один из типов, которые сервер сам даёт файлам (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `video/mp4`, `video/webm`); любой другой (страница, скрипт, SVG) окно получает как `application/octet-stream`. Заголовок `x-content-type-options: nosniff` — всегда.

### 9.6. Как проверить самому

Нужен OpenSSL 3.5 или новее.

```
openssl s_client -connect <адрес>:7350 -tls1_3 -groups X25519MLKEM768 -showcerts
```

Должно быть `Negotiated TLS1.3 group: X25519MLKEM768`, два сертификата (`CN=hatavoice.invalid` и `CN=HataVoice server`), а ключ второго сертификата — тот самый SK из приглашения (`sk=…`). Строка `Verification error: self-signed certificate in certificate chain` ожидаема: центра сертификации нет. С `-groups X25519` сервер отвечает `handshake failure`. Обычный HTTP получает 426: `curl -i http://<адрес>:7350/`.

## 10. Звонки: пересыльщик, `CallCredential v1`, ключи кадров, код звонка

Звонок шифруется сквозным ключом, который знают только его участники. Для каждого звонка люди в канале сами создают временную группу [MLS](https://www.rfc-editor.org/rfc/rfc9420) (RFC 9420); из её состояния каждый получает ключи кадров и код звонка. Сервер только пересылает непрозрачные сообщения группы и ничего в них не читает. Состояние группы, её ключи и ключи кадров живут только в памяти: на диск не пишутся, в логи не попадают и стираются при выходе из канала.

### 10.1. Параметры группы

| | Значение |
|---|---|
| Протокол | MLS 1.0 (OpenMLS 0.9, провайдер `openmls_libcrux_crypto`) |
| Шифронабор | `MLS_256_XWING_CHACHA20POLY1305_SHA256_Ed25519`, код `0x004D` (draft-ietf-mls-pq-ciphersuites); X-Wing — гибрид ML-KEM-768 и X25519, постквантовый |
| `group_id` | 16 случайных байт, их выбирает создатель звонка |
| Дерево | в расширении `ratchet_tree` внутри Welcome |
| Сообщения группы | только шифрованные (`PrivateMessage`) |
| В коммите | только `Add` и `Remove`; коммит с чем-то другим не применяется |
| Срок KeyPackage и листа | от 0 до `u64::MAX`: часы ПК в проверке не участвуют |
| Ключ подписи листа | Ed25519, **новый на каждый вход в звонок**, только в памяти |
| Учётные данные листа | `BasicCredential`, внутри `CallCredential v1` (10.2) |

### 10.2. `CallCredential v1`

Он привязывает временный ключ подписи листа к ключу личности человека — для этой группы и этого канала. Лист нельзя перенести в другой звонок, а сервер не может выдумать участника: у него нет чужого ключа личности. Байты (длина `146 + длина channel`):

| Поле | Размер | Что |
|---|---|---|
| версия | 1 | `0x01` |
| `ik` | 32 | публичный ключ личности (Ed25519) |
| `group` | 16 | `group_id` звонка |
| длина `channel` | 1 | 1–64 |
| `channel` | 1–64 | id канала, UTF-8 |
| `sig` | 32 | публичный ключ подписи листа MLS |
| `proof` | 64 | подпись ключом личности над сообщением ниже |

`proof` подписывает байты `b"hatavoice-call-cred-v1\n"` ‖ `group` ‖ `channel` ‖ `sig`.

Каждый участник проверяет каждый лист, который входит в группу (при входе по Welcome — все листы дерева, дальше — каждый новый и новый лист самого коммитящего):

1. Запись разбирается точно: версия 1, длина ровно по формату, `channel` — UTF-8 длиной 1–64 байта, после `proof` ничего нет.
2. `group` и `channel` — этого звонка.
3. `sig` равен ключу подписи листа MLS.
4. `proof` верен ключом `ik`.
5. `user_id(ik)` допущен по журналу участников: личность состоит в журнале, сейчас не забанена и имеет право `connect` в этот канал.
6. Один человек — один лист. Повторный вход заменяет лист: старый удаляется (`Remove`) в том же коммите, где добавляется новый.
7. Коммит сделан участником группы, а у нового листа коммитящего тот же человек.

Для Welcome проверяется ещё, что `group_id` — этого звонка, шифронабор — из 10.1, все листы прошли проверку и никто не состоит в группе дважды. Лист, не прошедший проверку, не принимается: `Add` с ним не коммитится, а полученный от другого коммит с ним считается сбоем (10.5). Добавляющий перед `Add` ещё проверяет, что человек сейчас виден в комнате LiveKit этого канала. Остальные этого не требуют: событие LiveKit о новом человеке может прийти чуть позже коммита.

### 10.3. Пересыльщик: маршруты

Все запросы подписанные (раздел 4). Допуск проверяется по порядку: сервер без владельца отвечает `503` (`unclaimed`); подписавший, которого нет в журнале, — `403` «Ты не участник этого сервера — нужна ссылка-приглашение» (`join_needed`, как в разделе 4); участник без права `connect` в канале (так же отвечают на запрос несуществующего канала) — `403 {"error": "Ты не в этом звонке"}`. Байты в JSON — base64url без `=`. Тела запросов: `join` до 16 КиБ, `create` и `commit` до 256 КиБ (больше — `413`).

| Маршрут | Дополнительное условие | Тело → ответ |
|---|---|---|
| `POST /api/call/{channel}/create` | человек сейчас в комнате LiveKit этого канала (сервер спрашивает LiveKit в обработчике) | `{"group_id"}` (16 байт) → `200 {"epoch": 0}`: звонок начат, в группе только создатель. Звонок уже есть: `409 {"exists": true, "group_id", "epoch"}` — нужно входить как новичок |
| `POST /api/call/{channel}/join` | в комнате LiveKit | `{"group_id", "key_package"}` (`group_id` — группа, в которую просится новичок, из ответа `create`) → `200 {}`; `404 «Звонка нет»`, в том числе когда у звонка канала уже другая группа: тогда ничего не меняется, а новичок начинает с `create`. Заявка кладётся в очередь, всем участникам группы, кроме самого новичка, уходит `call_join`. Если новичок сейчас в списке группы, сервер сначала убирает его оттуда: просьба войти значит, что группы у него больше нет (программа перезапустилась или сбросила группу); коммит, который добавит его снова, вернёт его в список. Если после этого в списке никого не осталось, звонок забывается сразу: новичку — `404 «Звонка нет»` (он начинает с `create`), остальным ожидающим — `call_reset` |
| `POST /api/call/{channel}/leave` | нет: в комнате LiveKit быть не нужно, LiveKit мог уже выбросить человека | `{"group_id"}` (группа, которой у человека больше нет) → `200 {}`; `404 «Звонка нет»`. Человек убирается из списка группы и из очереди заявок: группы у него больше нет (вышел из канала или сбросил группу, чтобы войти заново). Если список опустел, звонок забывается сразу, ожидающим уходит `call_reset`. Если у звонка канала уже другая группа, `leave` ничего не меняет и отвечает `200 {}`: выход ждёт ответа не больше 2 с, и запрос, дошедший позже, после возвращения человека в канал, не должен снять его со следующего звонка |
| `POST /api/call/{channel}/commit` | в комнате LiveKit и в группе по списку сервера | `{"group_id", "epoch", "commit", "members": [user_id…], "welcome": {"to": [user_id…], "message"} или null}` → `200 {"epoch": <новая>}`; `409 {"conflict": true, "epoch": <текущая>}`, если в эту эпоху уже принят другой коммит; `404 «Звонка нет»`, если у звонка канала другая группа |
| `GET /api/call/{channel}?since=N` | в группе, в очереди на вход или в комнате LiveKit (в том числе пока LiveKit переподключает человека) | `200 {"group_id", "epoch", "commits": [{"epoch", "commit"}…]}` — коммиты, сделанные в эпоху `N` и позже; `404 «Звонка нет»` |

Остальные ошибки: `400 «Неверный формат запроса»` (в том числе `join`, `leave` или `commit` без `group_id` из 16 байт), `400` с пояснением, если `group_id` не 16 байт или в `members` больше людей, чем в журнале, `404 «Звонка нет»`. Тело ошибки всегда `{"error": "…"}`.

Что сервер хранит про звонок канала, только в памяти: `group_id`, текущую эпоху, список участников, очередь заявок, **последние 64 коммита** и время последнего изменения.

Как сервер принимает коммит:

- Один коммит на эпоху: принимается тот, у которого `epoch` равен текущей. Эпоха растёт на 1.
- Отправитель должен быть в группе по списку сервера и остаться в присланном `members`.
- Присланный `members` сервер оставляет в виде списка группы: по нему он решает, кому слать события, от кого принимать следующий коммит и кому разрешать `GET`. Каждый человек остаётся в нём один раз, и только если по журналу имеет `connect` в канале. Солгать в списке может только участник звонка, и ложь портит лишь этот самый звонок.
- Все, кто вошёл в группу этим коммитом, убираются из очереди заявок.
- Принятый коммит уходит событием `call_commit` прежнему и новому составу группы, кроме отправителя (10.4).

Сервер забывает звонок в двух случаях:

- Список группы опустел: последний из него вышел (`leave`) или попросился войти заново (`join`). Звонок забывается сразу, ожидающим (кроме того, кто сам об этом попросил) уходит `call_reset`.
- В комнате LiveKit канала нет ни одного участника группы и с последнего изменения (создания звонка или принятого коммита) прошло не меньше 5 секунд. Проверка идёт в том же опросе комнат раз в 2 секунды; если LiveKit ответил не полностью, звонки не трогают. Группе и ожидающим уходит `call_reset`.

### 10.4. События звонка

Приходят по потоку событий (раздел 7) только людям этого звонка. Содержимое для сервера непрозрачно. `call_join`, `call_commit` и `call_reset` несут `group_id` группы звонка: событие, дошедшее с опозданием от прежнего звонка этого канала, клиент пропускает. Клиент принимает их, только если `group_id` — группы, в которой он состоит или в которую попросился; пока он ни в какой, `call_join` и `call_commit` берутся, а `call_reset` — нет.

| Событие | Кому | Поля |
|---|---|---|
| `call_join` | участникам группы, кроме самого новичка | `channel`, `group_id`, `user` (кто просится), `key_package` |
| `call_commit` | всем из прежнего и нового списка `members`, кроме отправителя (свой коммит отправитель применяет сам после `200`). Тот, кого коммит удалил, получает этот коммит, как и положено в MLS: из него он узнаёт только то, что его удалили, и входит заново. Следующих коммитов он уже не получает | `channel`, `group_id`, `epoch` (эпоха, **в которой** сделан коммит, то есть до него), `commit` |
| `call_welcome` | только людям из `welcome.to`, которым по журналу разрешён канал | `channel`, `welcome` |
| `call_reset` | группе и ожидающим, когда сервер забыл звонок по опросу комнат; только ожидающим, когда список группы опустел (10.3) | `channel`, `group_id` забытого звонка |

Порядок не гарантирован. Сервер рассылает события уже после того, как отпустил блокировку, поэтому `call_commit` для эпохи N+1 может прийти раньше, чем для N. Получатель сравнивает `epoch` события с эпохой своей группы:

- равна — применить коммит;
- больше — пропущен хотя бы один: взять недостающие через `GET /api/call/{channel}?since=<своя эпоха>` и применить по возрастанию эпох;
- меньше — уже применён (или это свой): пропустить.

Так же догоняют и после обрыва потока событий: клиент после переподключения помечает группу «отстала» и спрашивает `since`. Если сервер уже не помнит нужных коммитов (дальше 64) или у звонка другой `group_id`, группа стирается и программа входит заново.

### 10.5. Вход, выход, сбои

Вход в канал:

1. Программа получает пропуск LiveKit и подключается к комнате **без публикации микрофона**, при этом E2EE в комнате уже включено.
2. `create`. `200` — человек создатель (эпоха 0). `409` — `join` с KeyPackage для группы из ответа.
3. Добавляющий (ниже) проверяет новичка по 10.2 и делает один коммит: `Add` (и `Remove` старого листа, если тот был) с Welcome для новичка.
4. Остальные применяют коммит, новичок применяет Welcome (проверив все листы). Теперь у всех новая эпоха, новые ключи (10.6) и общий код (10.7). Новичок сразу отдаёт ключи окну и публикует микрофон. `GET …?since` он спрашивает уже после этого и только если, пока ждал Welcome, видел коммит из эпохи Welcome или новее (события могут обгонять друг друга, 10.4) или поток событий прерывался.

Кто коммитит: участники группы, видимые в комнате LiveKit, упорядочиваются по номеру листа. Первый коммитит сразу, **k-й (от нуля) — через k × 2 секунды** после того, как изменение понадобилось, и только если нужный коммит так и не пришёл. Поэтому, если очередной добавляющий завис, не выйдя из комнаты (LiveKit ещё 15–20 секунд считает такого участника в комнате), следующий добавит новичка через 2 секунды. Проигравший гонку получает `409`, применяет принятый коммит и, если изменение всё ещё нужно, повторяет. Одновременные изменения (двое вошли, один вышел) складываются в один коммит.

Выход: как только человека больше нет в комнате LiveKit (вышел, выгнан, перенесён, забанен, отвалился сверх окна переподключения LiveKit) или журнал перестал допускать эту личность, очередной по порядку участник группы коммитит `Remove`. Ключи меняются: чужие новые ключи каждый ставит сразу, а свой включает для отправки через 250 мс (10.6, чтобы не было щелчков). Поэтому примерно 250 мс после `Remove` остальные ещё отправляют кадры на ключах прежней эпохи, и эти кадры удалённый мог бы расшифровать, если SFU ему их ещё пересылает (взломанный сервер может тайно оставить человека в комнате). После этого — ничего: ключей новой эпохи у удалённого нет, для остальных такого участника уже нет.

Программа, которая выходит из канала (или переходит в другой), шлёт `leave` с `group_id` своей группы (или той, в которую попросилась) и стирает группу. Ответа она ждёт не больше 2 секунд: недоступный сервер не должен задерживать следующий звонок. Если запрос всё-таки дойдёт позже, когда человек уже вернулся в канал, сервер увидит в нём прежнюю группу и ничего не изменит.

| Ситуация | Что происходит |
|---|---|
| Коммит или Welcome не применился, лист не прошёл проверку, пропущенную эпоху не догнать, сам удалён из группы | Группа и ключи стираются, программа шлёт `leave` (если была в группе) и входит заново как новичок: пара секунд тишины только у неё |
| Сервер отказал в коммите (`403`: по его списку человека нет в звонке) | Возможно, пропущен коммит, который удалил человека. После паузы в 2 секунды программа сначала берёт `since`: нашёлся такой коммит — входит заново; нет — пробует снова, не чаще раза в 2 секунды |
| Программа вылетела и сразу запущена снова (`leave` не ушёл) | `create` → `409` → `join`: сервер убирает её из списка группы. Остались другие — её добавят заново; не осталось никого — звонок забыт, она получает `404` и создаёт новый |
| Ключи не пришли за **10 секунд** | Замок красный, «Не удалось зашифровать звонок», кнопка «Повторить». Микрофон не публикуется, чужой звук не воспроизводится. Режима без шифрования нет |
| Welcome не применился (скорее всего, он для KeyPackage, от которого уже отказались) | Перед новой заявкой пауза 2, затем 4, затем 8 секунд: так программа не отстаёт от Welcome навсегда |
| Один KeyPackage дважды | Не добавляется: клиент помнит хеши (SHA-256) уже добавленных и отвергнутых |
| Заявка участника, чей старый лист ещё в группе (перезапустился) | Остаётся в очереди, какие бы коммиты ни пришли, пока в дереве группы не окажется лист именно этого KeyPackage. Тогда забываются она и более ранние заявки того же человека |
| Заявок накопилось больше 64 | Самые старые отбрасываются |

### 10.6. Ключи кадров

Ключ отправителя с листом `i` в эпохе `e`:

```
MLS-Exporter("HataVoice media v1", u32_be(i) ‖ u64_be(e), 32)
```

Это экспортёр RFC 9420 (раздел 8.5): метка `HataVoice media v1`, контекст — 12 байт (4 байта номера листа и 8 байт эпохи, оба big-endian), длина 32 байта. Каждый участник считает ключи всех отправителей группы, отправитель — свой. Ключ принадлежит личности LiveKit с `identity` = `user_id` человека.

Передача в LiveKit (встроенное E2EE `livekit-client`, AES-GCM; своих примитивов нет):

| | Значение |
|---|---|
| Поставщик ключей | `BaseKeyProvider` с `sharedKey: false`, `ratchetWindowSize: 0`, `failureTolerance: -1`, `keyringSize: 16`, `keySize: 256` |
| Номер ключа в LiveKit | `e mod 16` |
| Чужие ключи новой эпохи | ставятся сразу |
| Свой ключ | первый — сразу, каждый следующий — через **250 мс**: за это время кадры на старом ключе доходят и расшифровываются (старые ключи остаются в кольце из 16 мест), поэтому щелчков при входе и выходе людей нет |
| Микрофон | публикуется только после того, как свой ключ установлен. До этого кнопка «Ждём ключи шифрования», а push-to-talk и голосовая активация ничего не передают. Уже опубликованный микрофон заглушается всякий раз, когда звонок перестаёт быть зашифрованным (группа потеряна и ключи новой ещё не пришли, или сбой): иначе голос шёл бы на ключе прежней группы. Ключи пришли — микрофон снова работает, как его оставил человек |

Ключи идут из Rust-части в окно событием `call-keys` `{address, channel, epoch, keys: [{identity, index, key}]}`; состояние звонка для интерфейса — событием `call-state` `{address, channel, state: pending | secure | failed, code, members, error}`. Ключ личности и состояние MLS в окно не попадают никогда — только короткоживущие ключи кадров.

Что окно воспроизводит:

- Только зашифрованные дорожки людей, которые есть в группе. Звук участника без ключей не воспроизводится, и в интерфейсе у такого участника пометка «не в шифровании».
- Если от человека хоть раз за звонок пришла незашифрованная публикация, его звук не воспроизводится до конца звонка, что бы ни показывали остальные дорожки той же личности: livekit-client выбирает расшифровку для личности целиком по её последней публикации, так что после одной незашифрованной дорожки остальные могли бы пройти открытыми.

### 10.7. Код звонка

Из `epoch_authenticator` текущей эпохи (RFC 9420, раздел 8) берутся **первые 30 байт**, делятся на 6 кусков по 5 байт. Каждый кусок читается как беззнаковое число big-endian, берётся остаток от деления на 100 000 и записывается пятью цифрами с ведущими нулями. Шесть групп через пробел:

```
ddddd ddddd ddddd ddddd ddddd ddddd
```

Код одинаков у всех в звонке и меняется при каждом входе и выходе. Его читают вслух: совпал — у всех одно и то же состояние группы, значит, посередине никого, и сервер не показал разным людям разные коммиты. Если в `epoch_authenticator` меньше 30 байт, кода нет (пустая строка).

## 11. Группа сервера (чат)

Одна постоянная группа MLS на сервер: в ней все участники журнала, по одному листу на человека. Через неё идут сообщения чата и голосования; сервер хранит и раздаёт только шифротекст.

### 11.1. Параметры

Шифронабор и правила группы — как у звонка (10.1). Учётные данные листа — `CallCredential v1` (10.2) с контекстом `@server` на месте id канала: id канала состоит только из `[a-z0-9-]`, поэтому лист группы сервера нельзя принять за лист звонка. В группу допускается участник журнала, не забаненный сейчас. Сообщение принимается только в текущей эпохе группы, ключей прошлых эпох клиент не хранит.

Группа сервера хранится на диске клиента снимком: `b"HVGS1"` ‖ SHA-256 тела ‖ тело (`group_id`, контекст, `user_id`, открытый ключ подписи листа, все записи хранилища OpenMLS по возрастанию ключа). Снимок держит все секреты группы и лежит только в зашифрованном файле.

### 11.2. Маршруты

Все — подписанные запросы участника журнала (`member_only`, раздел 4). Тела: `join` до 16 КиБ, `message` до 64 КиБ, `commit` до 256 КиБ. Байты — base64url без `=`; `group_id` — 16 байт.

| Маршрут | Тело → ответ |
|---|---|
| `POST /api/group/create` | `{"group_id"}` → `200 {"epoch": 0}` (создатель — единственный участник); группа уже есть — `409 {"exists": true, "group_id", "epoch"}` |
| `POST /api/group/join` | `{"group_id", "key_package"}` → `200 {}`; группы нет или она другая — `404 «Группы нет»`. Сервер хранит последнюю заявку каждого человека, пока её не исполнит коммит, и шлёт составу группы `group_join` |
| `POST /api/group/commit` | `{"group_id", "epoch", "commit", "members": [user_id…], "welcome": {"to": [user_id…], "message"} или null, "added": [SHA-256 в hex каждого добавленного KeyPackage]}`; заявки снимаются только те, чьи KeyPackage названы в `added` (кто попросился заново, пока коммит был в пути, остаётся в очереди) → `200 {"epoch": <новая>, "seq"}`; `409 {"conflict": true, "epoch"}`; отправителя нет в составе или он себя в нём не оставил — `403 «Ты не в группе сервера»`; другая группа — `404`. В `members` и `welcome.to` остаются только участники журнала; длиннее журнала — `400 «Слишком много участников»` |
| `POST /api/group/message` | `{"group_id", "epoch", "message"}` → `200 {"seq", "at"}`; эпоха не текущая — `409 {"conflict": true, "epoch"}`; не в составе — `403`; больше 30 сообщений за 10 секунд — `429` |
| `GET /api/group?since=N` | `200 {"group_id", "epoch", "members", "online", "entries", "more", "pending": [{"user", "key_package"}…], "welcome": {"epoch", "message"} или null}` — записи с `seq` > N, не больше 500 (`more` — есть ещё); `welcome` — только тому, кому он сделан, не старше 7 дней; `online` — кто из состава сейчас держит поток событий. Группы нет — `404` |
| `POST /api/group/withdraw` | `{"group_id"}` → `200 {}`: заявка отправителя снимается. Участник, который уже в группе и видит свою заявку (оставшуюся от прошлого запуска), отзывает её: иначе её KeyPackage вытеснил бы его рабочий лист |
| `POST /api/group/signal` | `{"group_id", "epoch", "message"}` (тело до 2 КиБ) → `200 {}`; сервер передаёт сообщение онлайн-составу событием `group_signal` и ничего не хранит; больше пяти за 5 секунд от человека — `200`, но лишние не передаются; не в составе — `403`; эпоха не текущая — `409 {"conflict": true, "epoch"}` |
| `POST /api/group/reset` | только владелец: `{"group_id"}` новой группы → `200 {}`; прежняя группа, журнал, заявки и Welcome забыты, владелец — единственный участник новой; всем участникам журнала — `group_reset` |

**Запись журнала группы:** `{"seq", "kind": "commit" | "message", "epoch", "sender", "data", "at"}`; у коммита ещё `members` (состав после него); у сообщения старше 90 дней `data` пустой и `"pruned": true`. `seq` идут с 1 без пропусков, `epoch` — эпоха, в которой запись сделана. Хранится в папке данных сервера, `group/` (`meta.json`, `log.jsonl`, `pending.json`); эпоха и состав выводятся из журнала.

### 11.3. События

| Событие | Кому | Поля |
|---|---|---|
| `group_entry` | составу группы, кроме отправителя; коммит — ещё и прежнему составу | `group_id`, `entry` (запись целиком) |
| `group_join` | составу группы | `group_id`, `user`, `key_package`, `online` |
| `group_welcome` | адресатам Welcome | `group_id`, `epoch`, `message` |
| `group_reset` | всем участникам журнала | `group_id` новой группы |
| `group_signal` | онлайн-составу, кроме отправителя | `group_id`, `sender`, `message` (сигнал MLS: «печатает…») |

### 11.4. Сообщения чата

Плейнтекст прикладного сообщения MLS — JSON, поле `t` — тип. Автор — человек листа-отправителя (его проверяет MLS), а не поле внутри; время — `at` записи журнала. Каждый клиент проверяет правила сам, по своему журналу участников, и молча пропускает то, что их нарушает (не JSON, лимиты, чужое сообщение, закрытый канал, повтор номера).

| `t` | Поля | Правило |
|---|---|---|
| `msg` | `id` (16 случайных байт, base64url), `ch` (id канала), `text` (1–4000 символов; 0–4000, если есть файлы), `reply` (id или нет), `files` (0–10 файлов `{blob, size, key, name, mime}`: `blob` — SHA-256 блоба в hex, `size` — до 25 МиБ, `key` — 32 байта base64url, `name` — до 200 символов, без `/ \ : * ? " < > \|`, управляющих и имён устройств Windows, `mime` — `тип/подтип`) | канал есть в журнале и не закрыт (ни у одной роли не запрещён `view`); файлы с нарушенным полем — пропуск всего сообщения |
| `edit` | `id`, `text` | только автор |
| `del` | `id` | автор или человек с `manage_channels` |
| `react` | `id`, `emoji` (до 16 байт), `on` | любой; не больше 20 разных эмодзи под сообщением |
| `poll` | `id`, `ch`, `q` (1–300), `opts` (2–10 по 1–100), `multi` | канал как у `msg` |
| `vote` | `poll`, `choice` (номера вариантов; пусто — отозвать) | один голос на человека, последний заменяет прежний; `multi: false` — не больше одного |
| `close` | `poll` | только автор голосования |
| `profile` | `p` — подписанный профиль `{user, nickname, color, at, signature}` (подпись над `["hatavoice-profile-v1", SK, user, nickname, color, at]`) | только свой (`user` — отправитель), подпись сходится с ключом этого сервера, ник 1–32 символа; берётся профиль с самым поздним `at` |

**Подпись автора.** У каждого события, кроме `profile`, рядом с полями — `sig`: Ed25519 ключом личности автора (base64url, 64 байта) над утверждением — JSON-массивом:

| Событие | Утверждение |
|---|---|
| `msg`, `edit` | `["hatavoice-chat-v1", SK, "msg", id, ch, text, reply или null, files]`; у `edit` — новый текст, а `ch`, `reply`, `files` из сообщения |
| `react` | `["hatavoice-chat-v1", SK, "react", id, emoji, on]` |
| `poll` | `["hatavoice-chat-v1", SK, "poll", id, ch, q, opts, multi]` |
| `vote` | `["hatavoice-chat-v1", SK, "vote", poll, choice]` |
| `close` | `["hatavoice-chat-v1", SK, "close", poll]` |
| `del` | `["hatavoice-chat-v1", SK, "del", id]` |

Подпись проверяется ключом отправителя (по журналу, в том числе бывшего участника). Событие без `sig` (прежняя версия) принимается по MLS, но не передаётся новичкам; с `sig`, которая не сходится, — отбрасывается.

Клиент шлёт свой `profile`, когда группа стала «готова» и последний отправленный в неё профиль другой, и сразу при смене ника или цвета.

**Пакет истории.** Чей коммит добавил людей (новичков или вернувшегося с новым листом), тот сразу шлёт `{"t": "pack", "to": [user_id…], "blob", "key", "size"}`: `blob` — SHA-256 блоба в `chat-media`, `key` — его ключ (как у файла чата), `size` — размер открытого текста (до 25 МБ). Внутри — JSON `{"v": 1, "profiles": [профиль…], "records": [{seq, at, sender, body}…]}`: последний профиль каждого и подписанные записи истории за `history_days` дней настроек сервера (0 — только профили) в открытых каналах — каждое живое сообщение и голосование в нынешнем виде (у правленого — `msg` с текстом и подписью последней правки и `"edited": true`), реакции, которые стоят, последний голос каждого, `close`; удалённое не идёт; не влезает в 25 МБ — уходят самые старые. Получатель берёт только записи с номером меньше номера `pack`, только события чата с подписью автора, сходящейся с его ключом, и строит модель из истории и пакетов вместе, по порядку номеров. Пакет не скачался — повтор при следующем запуске.

Упоминание в тексте — `<@user_id>`; окно показывает его как `@Ник`. Тип файла получатель определяет сам по первым байтам расшифрованного файла (`mime` — подсказка отправителя); в ленте показываются только PNG, JPEG, GIF, WebP, MP4 и WebM, остальное — карточкой «Сохранить».

**Сигналы** (`POST /api/group/signal`, событие `group_signal`) шифруются не прикладным сообщением MLS, а ключом эпохи: `export_secret("HataVoice signal v1", epoch как u64 BE, 32)`, XChaCha20-Poly1305, nonce 24 байта впереди, связанные данные — `user_id` отправителя (сервер не может приписать сигнал другому). Плейнтекст — `{"t": "typing", "ch"}` («печатает…», не чаще раза в 3 с), `{"t": "playing", "g"}` (игра, до 64 символов, или `null`; при смене игры), `{"t": "hello"}` (группа стала «готова»: каждый, кто во что-то играет, отвечает своим `playing`). Сигнал другой эпохи не открывается и пропускается. Игра человека гаснет по событию `online {online: false}`.

### 11.5. Хранение на клиенте

`<данные программы>\chat\key.bin` — 32 байта ключа под DPAPI, общего для всех чатов этого ПК; ключ, который DPAPI больше не открывает (переустановка Windows), откладывается, и начинается новый. На каждый сервер — папка `chat\<первые 16 байт SHA-256(ключ сервера) в hex>` (по какому бы адресу он ни был открыт; у одной личности на сервере один открытый чат) с файлами `group.bin` (снимок группы, 11.1) и `history.bin` (расшифрованные сообщения по одному на запись). Файл — записи `u32 BE длина ‖ nonce (24) ‖ XChaCha20-Poly1305`, связанные данные — имя файла. Испорченный снимок откладывается (`group.broken-<время>.bin`), и клиент входит в группу заново; оборванный хвост истории отрезается.

Блобы файлов клиент держит в `chat\<сервер>\files\<sha256>` как получил (зашифрованными) и сверяет SHA-256 при каждом чтении; окну отдаёт расшифрованные байты через `hvmedia` (`/chat/{адрес}/{sha256}`) только для файла сообщения, которое модель приняла, в канале, открытом сейчас.

Клиент применяет записи журнала группы по порядку `seq`: сначала дописывает историю, затем сохраняет снимок (сбой посередине перечитает те же записи, но не пропустит). Снимок сохраняется и до отправки сообщения: ключ этого сообщения уже израсходован, и перезапуск не должен найти его неиспользованным.

### 11.6. Файлы чата

Файл шифрует отправитель: случайный ключ 32 байта, XChaCha20-Poly1305, блоб = nonce (24 байта) ‖ шифротекст с тегом; открытого текста до 25 МиБ, блоб до 26 214 440 байт. Ключ, имя, тип и размер едут внутри сообщения группы (11.4), сервер хранит только блоб.

| Маршрут | Тело → ответ |
|---|---|
| `POST /api/chat-media` | подписанный запрос участника журнала, тело — блоб → `200 {"sha256", "size"}`; пустой — `400 «Пустой файл»`; больше предела — `413 «Файл больше 25 МБ»`; больше 20 загрузок за минуту от человека — `429 «Слишком много файлов — подожди минуту»`; все блобы вместе уже занимают 20 ГиБ — `507 «На сервере кончилось место для файлов»` |
| `GET /api/chat-media/{sha256}` | подписанный запрос участника → блоб (`application/octet-stream`); не hex-строка из 64 символов — `400 «Испорчена ссылка на файл»`; нет — `404 «Файл не найден»` |

Блобы лежат в папке данных сервера, `chat-media/<sha256>`; блоб удаляется через 90 дней после загрузки (повторная загрузка того же блоба продлевает срок).

## 12. Чего протокол не защищает

Что закрыто:

- Соединение с сервером и пропуск LiveKit не прочитать в сети (TLS 1.3, постквантовый обмен ключами). Подмену сервера программа видит по ключу.
- Звонок не слышат ни провайдер, ни чужой Wi-Fi, ни сервер (хост, а также взломанный сервер или ПК хоста, попавший в чужие руки): у них только шифр. Ключи звонка живут в памяти и стираются после звонка, поэтому записанный звонок не расшифровать, даже украв потом ключ личности. Обмен ключей постквантовый и на соединении, и в группе звонка — против «запишем сейчас, расшифруем потом».
- «Призрак» под чужим именем, которого выдал бы взломанный сервер, ключей звонка не получает: ключа личности у подставного участника нет, а проверка 10.2 требует подписи им.
- Подделать запись журнала или команду модерации от чужого имени не может даже хост: клиент проверяет каждую строку журнала действий по журналу участников или по подписи команды (сервер хранит её исходное тело в `request_body`) и помечает непроверяемые.

Что остаётся:

- Чат и голосования сервер не прочитает и не подделает (11), но видит, кто, когда и сколько пишет, и ставит время сообщений; он может не доставлять сообщения или не пускать в группу. До следующего блока (А2б-2) сервер видит ники, аватарки, названия каналов, «Играет в …» и кто в каком канале и когда. Хост видит ещё и с какого IP заходили, может выключить сервер или стереть его данные.
- Провайдер или кто-то в той же сети видит, что с IP хоста идёт звонок WebRTC, и объём трафика, но не содержимое. Маскировки трафика нет.
- Сервер видит, когда человек говорит, но не что: уровень громкости в заголовке RTP в WebRTC не шифруется. Индикатор «говорит» в программе считается локально.
- Взломанный сервер может не пускать людей в звонок или рвать его (отказ в обслуживании), но не может подслушать, добавить слушателя без ключа личности участника журнала или подделать запись журнала.
- Наказания исполняет сервер, а не клиент: при каждом опросе LiveKit (раз в 2 с) он выбрасывает из комнат тех, кому журнал не разрешает войти, и снимает право публиковать звук с заглушённых; прокси `/rtc` не пропускает пропуск, который журнал больше не разрешает. Сервер, который не станет этого делать, оставит такого человека в комнате, но участники группы сами удалят такого человека из группы (журнал больше не допускает эту личность), и новых ключей у него не будет.
- После удаления из группы (выход, кик, бан, перенос) остальные ещё примерно 250 мс отправляют на ключах прежней эпохи: свой новый ключ каждый включает с этой задержкой, чтобы смена ключей шла без щелчков (10.6). Если взломанный сервер оставит удалённого в комнате, эти четверть секунды звука он расшифровать может; всё, что отправлено после, — нет.
- Профили (ник, цвет) подписаны, но хранятся только на сервере и не входят в журнал: старый профиль сервер может «забыть», выдать чужой — нет.
- Заражённый ПК участника и запись звонка самим участником вне защиты.
